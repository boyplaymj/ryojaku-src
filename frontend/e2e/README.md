# e2e/ — 發團表單兩步驟精靈的瀏覽器實跑驗收

```bash
cd frontend && npm run e2e
```

## 為什麼有這一支

A3-c 把發團表單改成兩步驟精靈，改動**全部是 UI 行為**。而既有的三道閘對它零鑑別力：

| 閘 | 它證明什麼 | 對「按下去會發生什麼」 |
|---|---|---|
| `npm run typecheck` | 型別接得上 | 看不到 |
| `npm run build` | 打得包起來（esbuild **不驗型別**） | 看不到 |
| `npm test`（`run-tests.mjs`） | 純函式的行為 | 看不到 |

⇒ 這支是**唯一**會去按那顆按鈕的東西。

## rc 的意思（不可互相讀錯）

| rc | 意思 |
|---:|---|
| 0 | 全部通過 |
| 1 | 有測試沒過 |
| 2 | 腳本自己爆了 |
| 3 | **量不到** —— 測試中途頁面被 dev server 重載，紅綠都不可信，請重跑 |
| 4 | **沒有儀器** —— playwright 找不到／dev server 起不來／harness 生不出來 |
| 5 | 測試**通過**了，但**收尾沒收乾淨**（port 沒釋放，或根本判不出來）—— 見下方「收尾」 |

🔴 **4 與 5 不可以互相跑進對方的格子。** `portwait.sh` 載入失敗時回的是 **4**（沒有儀器），
不是 5 —— 少了那道守衛,它會變成 `command not found` ⇒ `CLEANUP_STATE=127` ⇒ 報成 5,
於是「收尾判定整段不存在」被講成「收尾沒收乾淨」。

⚠️ 這裡刻意不寫「共 N 種」：那個數字加一列就自動說謊，而且沒有任何徵兆。

🔴 **3 和 4 都不是「失敗」。** 把它們讀成失敗會產生假警報，把它們讀成通過會產生假綠燈。
（rc=3 這一格是真的發生過才加的：2026-09-06 第一次跑時 vite 送了
`✨ optimized dependencies changed. reloading`，元件重新掛載成一張空表單，
於是 T4 出現「按鈕永遠 disabled」這種**看起來很像產品缺陷**的假紅。
現在腳本會先開一頁暖機把 dep optimization 做完，再用 `load` 事件計數當第二道。）

## 🔴 收尾：port 一定要放掉，而「放掉了」必須有 exit code（2026-09-07 覆驗第二輪）

覆驗抓到兩件事，兩件都是**外觀完全正常**的失效：

| | 缺陷 | 為什麼看不出來 |
|---|---|---|
| ① | 收尾失敗只印一行 stderr，**rc 照樣是測試的 rc** | 那道「port 一定放掉了」的保證**沒有 exit code**；下一次撞 `--strictPort` 會看起來像「port 被別人佔著」 |
| ② | `fuser "$PORT/tcp"` 的 rc 被當**布林**用 | fuser 不可用（rc=127）／權限不足／任何 fatal error **全被讀成「port 空著」**⇒ fail-open |

② 的實測（遮蔽 `fuser`）：**rc=0、11/11 全綠、零警告，而跑完 port 還在監聽。**

修法分兩塊：

- **探測改三態**：`busy` / `free` / **`unknown`**，判不出來就回 unknown，由呼叫端 fail-closed。
  優先用 `ss`（它的 rc 有意義），`fuser` 只是退路。
  ⚠️ 誠實的限制：走 fuser 那條路時 `rc=1` 同時代表「沒人使用」與部分錯誤，man page 沒給它們不同的碼 ⇒ **free 與某些錯誤仍然分不開**。
- **收尾失敗蓋掉 rc**：`CLEANUP_STATE != 0` ⇒ `exit 5`。
  ⚠️ **只在測試本身通過時才蓋上去** —— 測試紅了保留 1/2/3/4，那是更重要的訊號，不可以被收尾問題遮掉。

### 為什麼 `wait_port_release` 住在 `portwait.sh` 而不在 `run.sh` 裡

它的兩條失敗路徑（等不到／探測不出來）**在真實環境裡造不出來** —— 要讓「自己起的 dev server
在 SIGTERM＋SIGKILL 之後 8 秒還佔著 port」是不可能的。⇒ 那兩條分支永遠不會被執行到，
於是「**寫對了**」與「**寫成恆真**」在結果上逐字相同。抽成函式＋可注入的探測器之後才有尺：

```bash
bash e2e/portwait.test.sh      # 它自己會印 N 過 / M 紅
```

（含 T8 那條把 `ss` 與 `fuser` **一起遮蔽**的反控，以及 T7／T10 那兩條「少了它，前一條可能只是恆真」的正反控。）

### 這道保證會不會紅？（2026-09-07 實跑）

**一、rc=5 的接線**（注入 `PORT_PROBE_CMD`，讓探測器回固定值）：

| 注入 | 預期 | 實際 |
|---|---|---|
| 一律 `free` | rc=0（**控制組**：證明 rc=5 不是「注入本身」的產物） | ✅ rc=0、11/11 |
| 一律 `unknown` | rc=5，訊息說「這**不是**已經放掉了」 | ✅ rc=5、`CLEANUP_STATE=2`、11/11 |
| 一律 `busy` | rc=5 | ✅ rc=5、`CLEANUP_STATE=1`、11/11 |

⚠️ **這三列量到的是「rc 與訊息對不對」,不含「SIGKILL 真的送出去了」** —— 那一半我沒在
端到端這條路上觀測到,它由 `portwait.test.sh` 的 T3 用注入的假 `kill` 覆蓋(斷言收到的
逐字是 `-9 111 222`)。本來寫成「rc=5,**且有升級 SIGKILL**」是把沒量的那一項
跟量到的那一項寫在同一格 —— 合取式只驗了第一項。

**二、port 到底有沒有放掉**（量「`run.sh` 回 rc 的那一瞬間，port 5199 還在不在監聽」）：

| | rc 回來時仍在監聽 |
|---|---|
| 現行收尾 | **0 / 6** |
| 反控：探測器恆回 `free`（＝修好之前的 fail-open） | **6 / 6** |

反控那一欄逐字重現了覆驗當初量到的 6/6 ⇒ 這把尺**不是恆綠**。

🔴 **而「連續重跑 6 次都沒撞 `--strictPort`」這件事不可以拿來當證據 —— 我量過，它零鑑別力。**
現行收尾 6 連跑 6/6 綠，**而 fail-open 那一版 6 連跑也是 6/6 綠**。
原因是兩輪之間還隔著 `npx vite` 啟動、harness 生成、找 playwright 那幾秒，
遠大於殘留的 ~0.1 秒 ⇒ 那個窗根本落不進去。
⇒ 要驗這件事就得**直接量 port 的狀態**（上表），不能用「重跑會不會撞」當代理。

## 十一條在驗什麼

| | 斷言 |
|---|---|
| T1 | 未定位 ⇒「下一步」**禁用**，且畫面上只有第一段 |
| T2 | 填入測試資料（寫 `coordinates`）⇒ 按鈕**解禁** |
| T3 | 籌碼 `''` ⇒ **瀏覽器原生 `required`** 擋下（submit 事件沒派送、焦點回到該欄、2.5 秒窗內沒有 toast） |
| T4 | 籌碼 `'   '` ⇒ 原生**放行**、submit **有**派送，改由 `validateCreateGameStage1` 跳 toast 且沒有前進 |
| T5 | 合格 ⇒ 進第 2 步，第一段卸載、第二段掛上 |
| T6 | 上一步 → 下一步 往返後，第一段欄位、第二段選項、照片**都還在** |
| T7 | 第 2 步送出 ⇒ 服務條款彈窗（API 不會被呼叫） |
| T8 | **全部頁面**都沒有非白名單請求（這條在 try 之外，一定會跑，而且會影響 rc） |
| T9 | 草稿帶回**過期**的開局時間 ⇒ 沒碰過就自動推進，使用者一字未改也能過 Stage1（[A3-i]） |
| T10 | **送出去的 payload** 帶的是刷新後的時間（在第 2 步停留超過一分鐘之後送出，[A3-i]） |
| T11 | **四顆誘餌**：`origin`／`pathname`／`GET` 三個條件每一個都不可少（每顆只變一維） |

🔴 **T3 和 T4 必須成對看。** 原生 `required` 只擋真正的空值，`'   '` 它會放行 ——
只有這一對的**對比**才分得出「原生擋的」與「程式閘擋的」。
T3 自己對「按鈕根本沒作用」零鑑別力（實測見下）。
同理 T1/T2 是同一顆按鈕的反向斷言：少了 T2，T1 對「按鈕永遠 disabled」零鑑別力。

## 一條紅了就停（以及為什麼 rc 要分 1 和 2）

T1–T7 是**一條接一條推進同一個表單狀態**的（T8／T9 不是，見下），所以 `ok()` 一發現紅就中止，剩下的標「未跑」。

理由是實際踩到的：突變 A（拿掉 `stakes` 檢查）會讓畫面在 T4 就跑進第 2 步，
接著 T5 去 `fill` 那個**已經卸載**的籌碼欄位必然拋 locator timeout ——
第一版就這樣把一次**真的抓到回歸**收成 `rc=2 腳本自己爆了`。
現在的歸屬規則：**已經有一條紅了 ⇒ 例外算後果（rc=1）；一條都沒紅卻爆掉 ⇒ 才是設備問題（rc=2）。**

## 這把尺會不會紅？（2026-09-06 四發，全部實跑過；2026-09-07 改共用時鐘後**重跑四發，結果相同**）

| 動的東西 | 預期 | 實際 |
|---|---|---|
| 拿掉 `validateCreateGameStage1` 裡的 `stakes` 檢查 | T4 紅 | ✅ T4 紅、rc=1，**且畫面停在「步驟 2 / 2」**（真的漏進去了） |
| 「下一步」`type="submit"` → `type="button"` | T3 紅 | ✅ T3 紅、rc=1（`焦點回到籌碼欄=false`、`submit次數=0`） |
| `HOME` 指到不存在的目錄（找不到 playwright） | rc=4 | ✅ rc=4，訊息講「沒有儀器不是量到失敗」 |
| 拿掉 `index.html` 的 `src="/index.tsx"` 錨點 | rc=4 | ✅ rc=4，拒絕生成 harness |

🔴 **舊版有一個盲區，2026-09-07 補掉了**：突變 B（`type="button"`）之下**舊的 T3 是綠的** ——
「原生擋住了」與「按鈕根本沒作用」在它眼裡逐字相同（兩者都是「沒 toast、沒前進」）。
補的方式是加兩個**正控**：`document.activeElement`（原生驗證失敗時瀏覽器會把焦點移到該欄）
與 `<form>` 上的 **submit 事件計數器**（原生驗證失敗時瀏覽器**不會**派送 submit）。
現在突變 B 由 T3 咬住，而且訊息直接說出是哪一種。

## 🔴 T4／T5 曾經間歇假紅 —— 根因與修法（2026-09-07）

症狀：同一顆 commit、同一份工作樹，**約每 4～5 次會紅一次**，訊息是「toast 沒出現」而
畫面停在步驟 1、第二段 0 —— 跟「閘門正常擋住但沒給訊息」長得幾乎一樣。

查的過程留下來，因為前兩個假說**都是錯的**：

| 假說 | 怎麼排除的 |
|---|---|
| ① 固定 sleep 取樣不到（toast `duration` 3000ms 會自己消失，窗兩端封閉） | 改成閂住式 `MutationObserver`（出現過就記住）＋上限 20s，**照樣紅** |
| ② 原生驗證氣泡吃掉下一次點擊 ⇒ 那一下沒送出表單 | 加 submit 計數器後量到 `submit有派送=true`，**不是這個**（把 Escape 拿掉連跑 5 次也沒重現） |
| ③ **跳出來的是另一句 toast** | ✅ 就是它 |

根因：表單的 `startTime` 預設 = **開頁那一刻**截到分的時間，而檢核① 拿它跟
「現在（秒歸零）」比 ⇒ **只要測試跑過一個分鐘邊界，第一個跳出來的就是
「開局時間不能早於目前時間」**，`validateCreateGameStage1` 委派的四道在 `stakes` 之前，
所以永遠輪不到「請輸入籌碼」。機率 ≈（開頁到該步驟的秒數）/ 60 —— 與觀察到的頻率吻合。

修法：`page.clock.setFixedTime()` 釘住 `Date.now()`／`new Date()`（timer 照常跑）。
**反控成立**：`E2E_NO_CLOCK_FIX=1` 關掉它，第 4 次就重現，而且訊息直接指出是哪一句 toast。

⚠️ **那句「反控成立」是 A3-i 之前的讀數，現在別再拿它當現況。** A3-i 讓過期的
`startTime` 自動推進 ⇒ 那句 toast 結構上跳不出來了，這個旋鈕多半跟
`E2E_WARM_CLOCK_SKEW_S` 一起失效（見下方「語意翻面了」那節）。
🔴 **但我只跑了 2 次全綠，那不構成「已失效」的證據** —— 它本來就是機率性重現的
（基準率個位數 %），2 次對這個區別幾乎沒有鑑別力。**這一格不是「量到綠」。**

⇒ 這裡刻意**不**去補那 60 輪。理由是有一個更強的證據，而且已經有了：`refreshStaleStartTime`
的呼叫點涵蓋**兩條**產生過期 `startTime` 的路徑（`CreateGroup.tsx:115` 草稿還原、
`:367` Stage1 閘門前），⇒ 未碰過的過期時間在檢核① 之前必被推進，那句 toast **結構上**
跳不出來。支持它的實驗就是上表那一組：把 `refreshStaleStartTime` 改成 `return null`，
同一個旋鈕立刻 3/3 全紅。
🔴 **但要說清楚這是哪一種話**：上面是**程式路徑的推論** ＋ 一組打在 A3-i 上的反向實驗，
**不是**對 `E2E_NO_CLOCK_FIX` 這個旋鈕本身跑到統計顯著。兩者不可互相冒充。
60 輪能回答的是「這個旋鈕現在還會不會紅」;它回答不了、也不需要回答「為什麼」。

### 🔴 第二層：一頁一個固定時間是不夠的（2026-09-07 下午，同一天量到）

第一版對暖機頁與正式頁**各**呼叫一次 `setFixedTime(new Date())`，兩者相隔約 4 秒。
而 `CreateGroup` **每次掛載都會把草稿寫進 `localStorage`** ——「載入草稿」那支 effect
宣告在「自動存檔」那支前面，它把 `isInitialMount` 設成 false，所以自動存檔在第一次
掛載就會跑（不必有任何欄位變動）。暖機頁與正式頁又**共用同一個 browser context**
⇒ 正式頁讀回的 `startTime` 是**暖機頁那一分鐘**的。

⇒ 假紅的窗只是從「開頁到 T4」縮成「暖機到正式頁」，**沒有被消掉**：
實測 **20 輪紅 1 輪**（≈5%，與 4 秒／60 秒相符），訊息仍是那句
`🔴跳的是「開局時間不能早於目前時間」`。

修法：`FIXED_NOW` 一個瞬間，兩頁共用。

🔴 **這一層漏掉的原因是我用了不夠力的尺**：修完那次「連跑 8 次全綠」被我當成證據，
但**在 5% 的殘餘機率之下，連 8 次全綠有 66% 的機會發生** ⇒ 那 8 次對「修好了沒」
幾乎沒有鑑別力。**重跑次數要用「修完之後預期的機率」去設**，不是憑感覺挑一個數字。
現在的正控是 **60 輪全綠**（若 5% 仍在，只有 4.6% 的機會發生）。

🔴 **而且新的反控是確定性的，不再靠機率重現**：
`E2E_WARM_CLOCK_SKEW_S=60` 故意把暖機頁的時鐘往前撥一分鐘，讓草稿帶著上一分鐘的
`startTime` 回來 —— 實測 **3/3 全紅**，訊息正是同一句。
（舊的 `E2E_NO_CLOCK_FIX=1` 留著，它關的是整個機制；新的這支專打「兩頁不同步」。）

🔴 **這不是把產品缺陷藏起來**，見下一節。

改動這十一條之後**請重跑上面那幾發突變**，否則「全綠」與「尺壞了」在結果上長得一樣。

## 🔴 T9 的兩件事：自己的 context、以及編號不等於執行順序

T9 造的場景是「草稿帶著過期的開局時間回來」，而草稿住在 `localStorage`。
**沿用正式頁那個 context 不行** —— 那裡已經有一份 `startTime = 現在`（＝不過期）的草稿，
會把要造的場景蓋掉，而那樣 T9 會綠、**綠得毫無理由**。所以它自己開一個 context。

也因此它**不吃前面七條推進出來的表單狀態** ⇒ 放在 try 之外，前面紅了它照樣量得到。

⚠️ **執行順序是 T1…T7 → T9 → T10 → T8**：T8 斷言的 `blocked` 要涵蓋 T9／T10 那兩頁，就必須排在它們後面。
編號是斷言的身分，不是執行順序。

## 順手量到的產品問題（**不是**本套件的缺陷 —— 2026-09-07 已修，見下一節 [A3-i]）

上面那個根因同時是一個真的使用者問題：**發團頁開著超過一分鐘，預設開局時間就變成過去**，
使用者一個字都沒改也會被「開局時間不能早於目前時間」擋下來。
它**先於 A3-c 就存在**（`validateCreateGame` 是 A3-a 從 `confirmCreate` 逐字搬出來的），
但精靈化之後它會在「下一步」就打到人，而不是等到最後送出。
⚠️ 本套件刻意用固定時鐘把它排除在觀測之外 —— 它與「兩步驟精靈對不對」無關，
留在裡面只會讓這十一條變成擲骰子。**要不要修是另一個決定。**

🔴 **草稿讓這個缺陷比「開著超過一分鐘」嚴重得多**（2026-09-07 追加，查第二層根因時撞到）：
`utils/draftStorage.ts` 的草稿有效期是 **24 小時**，而草稿裡存著 `startTime`。
⇒ 使用者填到一半離開、隔天回來，草稿一還原，`startTime` **必然**是過去的時間 ——
他一個字都沒改，按「下一步」就被擋。「開著超過一分鐘」只是這個問題最輕的那一種。
⇒ 修法拍板時要一起決定：還原草稿時那個過期的 `startTime` 怎麼辦。

## [A3-i] 那個產品問題的修法（2026-09-07，使用者拍板「touched 旗標・validate 不動」）

🔴 **關鍵是分得出「預設值餿掉」與「使用者故意填了過去的時間」** —— 這兩者在
`validateCreateGame` 眼裡逐字相同，所以它沒辦法只放行前者。⇒ 加一個 `startTimeTouched`
旗標（唯一會把它設成 true 的地方是 DatePicker 的 `onChange`），然後：

- **`validateCreateGame` 一行都沒動** —— 早於現在就是拒絕。使用者手動填過去的時間
  仍然被擋（A3a-15／A3a-17／A3c-09 那幾條斷言的正是這個行為，它們是對的）。
- 修在 UI 層：`refreshStaleStartTime({ startTime, touched, now })` 回傳新字串＝要覆蓋、
  `null`＝不要動。呼叫點三處：草稿還原時、Stage1 閘門前、最後送出前。
- 草稿多存一個 `startTimeTouched?`（optional，舊草稿讀回 `undefined` 當 false ——
  草稿存活 24 小時，裡面那個時間**必然**已經過去，當成「使用者選的」會讓他一還原就被擋）。
- 「什麼叫過期」只留一份：`isStartTimeInPast()`，檢核① 與自動推進都呼叫它。
  各寫一次比較式的話，只要差一個 `<`／`<=` 就會出現「推進了但驗證仍然擋下來」這種
  從畫面上完全看不出原因的死結（A3i-05 就是釘這件事的反控）。

### 這一組的突變（2026-09-07 實跑）

| 動的東西 | 預期 | 實際 |
|---|---|---|
| `refreshStaleStartTime` 直接 `return null`（＝根本沒修） | T9 紅、純函式紅 | ✅ T9 紅（`進到第 2 步=false`）＋ A3i-02／05／06 紅 |
| 拿掉 `if (input.touched) return null` | A3i-01 紅 | ✅ A3i-01 紅（e2e 不動 —— 它沒有 touched=true 的路徑，見界線） |
| `isStartTimeInPast` 的 `<` 改成 `<=` | 邊界那幾條紅 | ✅ A3a-16／A3i-04／A3i-06 一起紅 |
| `confirmCreate` 組 payload 用回舊的 `formData` | T10 紅 | ✅ T10 紅（`payload=05:57 送出當下=06:07 同一分鐘=false`）|
| `confirmCreate` 連 `withFreshStartTime()` 都不呼叫 | T10 紅 | ✅ T10 紅（`沒有捕捉到 onCreate 的 payload` ——被檢核① 擋在門外）|

### 🔴 T10 是補回來的，而它讓我犯的兩個錯都值得留著

**錯一：我宣告了一個不存在的盲區。** 上面第四發突變一開始是**存活**的，我把它寫成
「payload 帶不帶新時間只有真的送出才看得到，本套件到彈窗就停 ⇒ 沒有尺」。
覆驗者指出 harness 的 `onCreate` **本來就是可觀測的送出邊界** —— 它就在
`createGroupWizard.harness.tsx` 裡，我從頭到尾沒往那裡看。
個資檢查那道閘也不是障礙：Playwright 對本機那個死路 URL `fulfill` 一份完整假 profile 即可，
不碰任何正式後端。⇒ **宣告「沒有尺」之前，要先把現有的縫都找過一遍**；
「我沒找到」與「不存在」是兩句不同的話，而寫進 README 的那句用了後者。

**錯二：補上 T10 之後，那發突變仍然存活，而 T10 是綠的。** 因為 Stage1 閘門那一次
`withFreshStartTime()` 已經把 state 刷新過了 ⇒ 走到 `confirmCreate` 時 `formData`
本來就是新的，「用 state」與「用回傳值」在那條路徑上**逐字相同**。
修法是讓時間**在進入第 2 步之後**才過期（`clock.setFixedTime(FIXED_NOW + 10 分鐘)`），
兩個變數才分得開 —— 那同時是個真實情境：使用者在第 2 步慢慢填環境選項超過一分鐘。
⇒ **一條新測試綠了不代表它咬得住**；要拿它宣稱的那個缺陷去打它一次才知道。

⚠️ T10 的判準是「payload 的那一分鐘 **等於** 送出當下的那一分鐘」，不是 `>=` ——
後者對「早了 10 分鐘」有鑑別力，對「晚了 10 分鐘」沒有，而兩者都是錯的。
⚠️ 假 profile 只證明「個資完整時走得下去」，**不證明個資檢查本身對不對**。

### ⚠️ 舊反控 `E2E_WARM_CLOCK_SKEW_S=60` 的語意翻面了

修之前它 **3/3 全紅**（暖機頁的草稿帶著上一分鐘的 `startTime` 進正式頁）。
修之後**同一個旋鈕 3/3 全綠** —— 因為產品端現在會自動推進。
⇒ 它從「設備 bug 的重現器」變成「**產品修法的獨立證明**」。

🔴 **「中間只差 A3-i 那幾行」這句原本是推的，2026-09-07 補做了反向實驗才算數**：
把 `refreshStaleStartTime` 改成直接 `return null`（＝把 A3-i 拿掉），同一個旋鈕
**3/3 全紅**，訊息逐字還是那句 `🔴跳的是「開局時間不能早於目前時間」`，
連帶 T9／T10 一起紅。

| `E2E_WARM_CLOCK_SKEW_S=60` | 結果 |
|---|---|
| A3-i 在（現況） | 綠 3 / 紅 0 |
| A3-i 拿掉（`refreshStaleStartTime` → `return null`） | 綠 0 / **紅 3** |

⇒ 綠的**原因**是 A3-i，不是「旋鈕壞了」。少了下面那一列，這兩件事在結果上逐字相同。

🔴 但要知道代價：**它不再守得住「兩頁時鐘被拆回各自 `new Date()`」那個回歸** ——
草稿自動推進之後，那個設備缺陷不再有可觀測的後果。守那件事的現在只剩程式註解。

🔴 **另一個代價：`E2E_NO_CLOCK_FIX=1` 之下 T10 是空的。** 那個旗標會一併跳過
第 443 行 `setFixedTime(FIXED_NOW + 10 分鐘)` ⇒ 沒有時間流逝，「payload 那一分鐘
等於送出那一分鐘」**恆真**。所以那個旗標只能拿來看假紅重不重現，
**不可以拿它跑出來的 11/11 當通過**。

## 🔴（沿革）收尾：`kill` 送出訊號 ≠ 行程已退出（2026-09-07 第一輪覆驗）

`cleanup()` 原本送完 `kill` 就結束。實測**腳本回 rc 的那一刻，6/6 次 port 5199 都還在監聽**，
約 0.1 秒後才消失。它不是孤兒（會自己走完），但「rc 回來了」與「port 已釋放」是兩件事 ——
緊接著重跑會撞 `--strictPort`，而那個失敗**看起來會像「port 被別人佔著」**，
查的方向整個錯掉。

修法（**第一版，已被上面那節取代 —— 讀到這裡請往回看「收尾：port 一定要放掉」**）：
`cleanup()` 等到 port 真的釋放為止（`fuser`）。5 秒不放升級 `SIGKILL`，
再 3 秒仍不放就**印警告連同占用者**（靜默的話，下一次那個莫名其妙的 rc=4 沒有任何線索）。

🔴 這一版有兩個缺陷，同一天的第二輪覆驗才抓到：**警告不影響 rc**（保證沒有 exit code），
以及**把 `fuser` 的 rc 當布林**（fuser 不可用就 fail-open）。現行版本是三態探測 ＋ rc=5，
邏輯搬到 `portwait.sh`。**本節保留的是當時的量測與推理，不是現在的實作。**

| | 回 rc 那一刻 port 還在監聽 |
|---|---|
| 修之前 | **6 / 6** |
| 修之後 | **0 / 8**（再量一次 0 / 6）|

實測等待長度 **0～4 個 0.1 秒 tick** ⇒ 這個迴圈既不是恆真、也不是空轉
（有一次 0 tick：那次 cleanup 之前就已經放掉了）。

⚠️ ~~**`SIGKILL` 升級與那句警告目前沒有反控**~~ —— 這句在當時是對的（造不出那個狀態），
**現在不是了**：邏輯抽進 `portwait.sh` 之後，那兩條分支由 `portwait.test.sh` 的
T3（永遠 busy → 升級 SIGKILL 且帶對 pid → rc 1）與 T4／T5（unknown → rc 2 且**不亂殺**）
用注入的假探測器覆蓋。⇒ 抽出去的**目的**就是這個，不是為了整齊。
⚠️ 那個等待只在「我們真的起過 server」時才做：早退時 port 上那個是別人的，
空等 8 秒再警告只會製造假訊號。
🔴 **但判斷「起過沒有」不可以用 `VITE_PORT_PIDS` 非空當代理**（本句 2026-09-07 訂正，
原文正是那樣寫的）：那個變數是探測工具的產物，工具一不可用它就是空的
⇒ **等待整段被跳過，而那正是最需要等的時候**。現在用獨立旗標 `VITE_STARTED`。

## 🔴 T10 的假 profile 是怎麼不把 T8 弄成假綠的（T11 存在的理由）

T10 要走完個資檢查那道閘，所以 `guard()` 對本機那個 `user-info` 回一份完整假 profile。
第一版的判斷是 **`u.includes('/user-info')`** —— 那是子字串比對：
`https://evil.example/?x=/user-info` 也會被 fulfill，於是它**不會進 `blocked`**，
**T8 那條安全斷言就變成假綠**。
（同一類的坑第二次犯：白名單一開始也是拿整條 URL 去 regex，被 query string 命中。）

現在改成解析後比 `origin` ＋ `pathname`，再釘 `GET`。而**光是改對還不夠** ——
沒有反控的話，改回子字串比對在結果上完全看不出來。⇒ T11 是它的反控。

實測（2026-09-07，把 `isProfileStub` 改回 `includes`）：
**T8 綠、T10 綠、只有 T11 紅**，而且 T11 直接印出誘餌拿到了假 profile、沒進被擋清單。
⇒ 那兩條對這個缺陷**零鑑別力**，這正是 T11 不能省的證明。

### 🔴 一顆誘餌不夠 —— 它同時變了兩個維度，殺得掉的只有 `includes`

第一版 T11 只有一顆誘餌（`https://evil.example/x/user-info`），而它**同時**「不同 origin、
不同 pathname」⇒ 對「只比 origin」「只比 pathname」「漏掉 GET」三種錯誤**零鑑別力**
（覆驗抓到的）。**反控要一次只動一維，否則殺掉的是哪一條無法歸因。**

現在是四顆，每顆只變一維：

| 誘餌 | 該被記錄？ | 殺掉哪個錯 |
|---|---|---|
| 錯 origin ＋ 路徑含 `/user-info` | ✅ 是 | `includes` |
| 同 origin ＋ **錯 pathname** | ❌ 否（本機在白名單 ⇒ `continue`） | 漏掉 pathname |
| **錯 origin** ＋ 同 pathname | ✅ 是 | 漏掉 origin |
| 同 origin ＋ 同 pathname ＋ **POST** | ❌ 否 | 漏掉 `GET` |

🔴 **判準分兩種，不能混**：本機 origin 在白名單內 ⇒ 那兩顆會被 `continue`（拿到 dev server
的回應），**不會進 sink**。對它們唯一有意義的問題是「有沒有拿到假 profile」。
把「一律要被記錄」套到四顆上，就會用一個假的判準去驗一件真的事。

突變實跑（每發只拿掉一個條件，四發都**只紅對應那一顆**）：

| 突變 | 結果 |
|---|---|
| `isProfileStub` 改回 `includes` | ✅ 四顆全紅 |
| 漏掉 pathname（改成比 origin ＋ `/__e2e_no_backend` 前綴） | ✅ 只紅「同 origin ＋ 錯 pathname」，其餘 10 條綠 |
| 漏掉 origin（只比 pathname） | ✅ 只紅「錯 origin ＋ 同 pathname」 |
| 漏掉 `GET` | ✅ 只紅「同 origin ＋ 同 pathname ＋ POST」 |

⚠️ **第二發原本寫的是「只比 origin」，那發不可歸因**：它會把 harness 自己的 HTML／JS
也 fulfill 成假 profile ⇒ 頁面根本載不出來，T11 紅在 `waitForSelector timeout`、
連 T1–T7 一起垮（8/11）。**那是「突變體壞掉」不是「被探針咬住」，兩者在紅燈上長得一樣。**
⇒ 改成保留前綴、只漏掉最後那一段，頁面正常、歸因乾淨。

⚠️ T11 用**自己的** sink，不把誘餌塞進 T8 那份清單（T8 斷言它必須是空的）。
⚠️ `E2E_API_BASE` 由 `run.sh` 傳進來，與 dev server 的 `VITE_API_BASE_URL` 是**同一個值**
（run.sh 的 `API_BASE`）。兩邊各寫一次的話，改了其中一邊 ⇒ T10 拿不到 profile、
走不到 `onCreate` ⇒ **會紅，不會靜默失效**。

## 兩道獨立的「不准碰正式後端」

1. `run.sh` 把 `VITE_API_BASE_URL` 指到本機死路。

2. Playwright 端把**非白名單**請求 `abort`，清單由 **T8** 斷言為空 —— 不是只印出來。
